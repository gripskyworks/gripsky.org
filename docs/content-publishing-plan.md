# GripSky 内容与发布系统：现状和下一步

日期：2026-10-02。范围：本地候选站 `gripsky-site-next` 的源码评估；没有查询或修改生产数据库、生产任务、真实订阅者或邮件投递。

## 现在实际能做什么

| 能力 | 当前实现 | 边界 |
| --- | --- | --- |
| 公共页面与双语路由 | `app/lib/site-data.ts` 定义页面、技能、版本；`app/[...slug]/page.tsx` 渲染 | 发布正文必须改源码、构建和部署；没有文章编辑后台 |
| SEO / 机器入口 | 页面元数据、`app/sitemap.ts`、`app/feed.xml/route.ts`、`llms.txt` | RSS 使用静态版本数组，站点地图的修改时间目前为固定日期，不随内容发布更新 |
| 订阅与退订 | `app/api/subscription/*`、`db/schema.ts`、`app/lib/server.ts` | 验证后入库；本地预览并不证明生产 SES 运行正常 |
| 联系 | `app/api/contact/route.ts` 写入请求，尝试邮件转发 | 没有工单管理台；转发失败时记录仍可保存 |
| 更新通知 | `app/api/internal/updates/publish` 创建发布记录及投递队列；`process` 小批量发送 | 这是通知队列，不会创建站内文章，也不会自动读取 Git 提交发信 |
| 内容管理 | 无 | 没有草稿、审稿、媒体库、后台登录或可视化编辑器 |

因此当前不是“纯前端空壳”：订阅、联系和邮件队列确实有服务端接口与数据库表。公开正文与版本目录则仍是源码中维护的内容。`update_publications` 记录的是一次邮件通知事件，不是公开文章的正本；不应把它误当 CMS。

## 早期组织站的推荐路径

先把**内容作为可审阅的文件**，暂不引入公开登录后台。个人维护、小规模更新时，后台的鉴权、文件上传、安全维护和数据迁移成本高于收益。现有 Git 历史天然提供差异、回退与来源，页面和邮件也能从同一份发布元数据生成。

### 阶段 A：整理内容正本

1. 将长文章、更新记录和研究日志从 `site-data.ts` 逐步迁到 `content/{en,zh}/...`。每篇采用 Markdown/MDX 正文及经过 schema 验证的元数据：共同 `id`、语言版 `slug`、`title`、`summary`、`author`、`language`、`translationStatus`、`status`（draft/published）、`createdAt`、`updatedAt`、`topic`、`canonical`、`source`。短而稳定的导航文案仍可留在 TypeScript。
2. 同一篇双语内容使用共同 ID、各自语言 slug 与翻译状态；没翻译时不制造空页面或虚假的 hreflang 配对。页面按发布日期与更新时间显示真实时间，不用构建时间冒充内容更新时间。
3. 建立构建前校验：重复 slug、错误内部链接、缺失标题摘要、错误日期、草稿泄漏、引用源缺失、图片替代文本。失败则不构建发布包。
4. 从同一份已发布内容生成页面、索引、RSS、站点地图与 `llms.txt` 导航；每条 RSS 指向自己的永久页面，不再全部指向版本列表。

### 阶段 B：把通知接到真正的发布事件

内容合并并部署成功后，先由公开 URL 回读验证 200、标题、规范网址与正确版本，再允许创建通知事件。通知发布记录使用内容的稳定 ID / 版本作幂等键，保留人工确认开关；不在每次站点构建时自动群发。投递队列继续沿用现有订阅偏好、退订、日限额和失败重试机制。前端更新列表与通知摘要来自同一个内容正本，避免“邮件说已发布、站内无文章”。

### 阶段 C：何时需要编辑后台

仅当出现多名经常写稿的人、非技术维护者需要改稿、或频繁的定时发布与媒体管理需求，再评估私有后台。那时至少需要独立身份验证、权限分工、草稿/预览、发布审计、媒体白名单与限额、回滚、备份，以及通知的二次确认。后台不是简单加一张 `articles` 表，也不应公开到无保护的管理路径。

## 可作为首个迭代的交付定义

- 一篇中英文研究记录能从文件渲染成独立页面；有可核对的作者、更新时间、永久链接和源文指向。
- 首页/研究索引、RSS、站点地图只读取已发布记录；`draft` 永不进入公开 HTML 和机器入口。
- 发布工具输出将变动的 URL 清单；部署核验通过后才允许人工确认通知。
- 新流程可在本地预览环境用合成订阅者完整演练，不给真实邮箱发信；迁移到生产前另行确认数据、密钥和任务调度。

本轮先完成设计与事实记录，未擅自引入 CMS、外部 SaaS、管理员账户或自动发信。是否实施阶段 A，应在用户选定本地候选版本继续开发时另开一个明确的内容迁移节点。

## 2026-10-03 收尾补充

本地邮件预览现在优先于 SES 配置：`LOCAL_EMAIL_PREVIEW=true` 时验证码与更新返回 preview，联系请求只记录、不转发，即使进程带有 SES 环境变量也不会外发。行为测试使用合成配置与网络桩，验证三个入口均不调用外部请求。继承的 `scripts/publish-update.mjs`、`process-updates.mjs` 仍指向原部署常用的 `127.0.0.1:3000`；本候选预览为 `localhost:3014`，不可直接将这两个运维脚本当成本地预览命令。

同日后续 SEO 修复已从本地 sitemap 移除不可靠的固定修改日期；联系页也不再声明固定 `dateModified`。这修正了上表中的当时状态，但没有实施阶段 A、补造文章或更新 RSS 日期。下一轮最小增量仍是一篇经主体确认的独立记录、真实日期与作者、两种语言关系，再由同一记录生成 RSS 和 sitemap；不是先装一个管理后台。
